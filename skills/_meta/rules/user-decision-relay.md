# User Decision Relay

Apply before concrete creation and whenever a workflow needs the user's choice, confirmation, authorization, clarification, or changed scope. This is a communication rule, not a new skill chain or data schema.

## Ownership And Delegation

Director is the top-level production main AI, loading director-orchestrate locally and owning user interaction, scope, authorization and creative coordination. Reviewer is a fresh independent acceptance subagent. For engineering, main delegates repository research, implementation and testing to engineering agents; production experts retain their craft.

Specialists and review coordinators delegate directly when Task and nesting actually support it. After an unavailable tool or explicit nesting/depth rejection, retain that capability finding and ask main to relay role, outcome, references, scope and constraints. Main returns actual results to the ORIGINAL requesting specialist, review coordinator or checker task, not a replacement owner. Ordinary task failure is not a depth rejection; do not change host depth. Later visual operations still require fresh tasks and text/file handoffs, never restoration of an image-heavy context. Missing required role/isolation is a blocker.

Director can author and write its own complete plot options and decision plans, present them and retain actual replies locally; no main-to-self relay is needed. Expert-authored packets remain intact through main's presentation and batch replies to their original task. The presentation, labels, context, conditions and checkpoint rules below apply to both.

## Intake Before Creation

Before concrete creation, the responsible role must know the relevant needs from the user's request, confirmed configuration or existing source materials, or have explicit scoped delegation to decide them. Read-only material diagnosis and capability lookup may precede intake. Do not invent candidates, scenes, outlines, asset designs or prompts, even in chat as a preview or clarification aid, while the relevant intake is inadequate.

Reuse known answers and ask only consequential gaps, not an exhaustive questionnaire. Offer to let the responsible role decide open preferences. Record the actual grant, role, scope and constraints in the existing commission/config context; silence, missing values and a generic role assignment are not grants. Delegated artistic details may remain undecided until that role develops them. The initial episode-duration target and its boundaries still require the user's confirmation and remain common across a series.

Resolve foreseeable consequential choices early, ONE decision at a time, not a future-settings dump. Once relevant initial choices are satisfied or delegated, later artistic details belong to the responsible owner. Requested preview materials need relevant intake first and approval at the user's specified checkpoint afterward; internal planning does not create a checkpoint. Reference examples cannot supply missing intent or authority.

For an unspecified plot in a creation request, enough baseline intent (such as a theme, premise or desired experience) permits Director to develop THREE candidate stories by default. A selected plot is the result, not a prerequisite, of this exploration; unrelated provider settings do not block it. Ask only if missing baseline intent would make exploration arbitrary. Explicit candidate counts override three; reuse supplied scripts, selected directions and prior scoped delegation rather than restarting selection. Do not substitute a "who decides?" question or genre labels for developed candidates. Each candidate includes motivations, conflicts, causal progression and an ending/emotional landing. Actual script and asset production still wait until their relevant choices are known or delegated.

## Concrete Technical Choices

Production uses [typed generation-task inputs](shot-inputs.md): Creator groups consecutive designed photographic shots, preserving durations, dialogue and cuts. `task-inputs/taskNN.json` has exactly `{shots,references}`, with filename-derived task_id independent of the first shot and at least one full-group MP4; optional PNGs and static clips retain their declared controls. Provider minimum/70% packing guidance applies to generation tasks, not photographic-shot durations. Grouping does not extend scene/episode budgets. Preserve fixed/inherited settings; reference assembly grants no paid video submission. Independent shot-input review targets each task manifest, including internal cuts, sound bridges and necessary external boundaries, not another approval handshake.

For every relevant unresolved technical field, Creator prepares concrete CURRENT provider-supported AND workflow-wired values, accessible explanations and practical differences, plus "Creator decides THIS field" naming its scope. Cover provider/model/ratio/resolution for images and video. Reuse fixed, inherited and delegated settings without reasking. Recommendations are not selections.

For images/video scopes, Creator supplies all foreseeable questions in dependency order: provider, model, compatible ratio, resolution. Include explicit compatible choices and branches, not lists implying all combinations work. Main applies only authored conditions, skips answered/fixed/inherited/delegated fields, and returns for model resolution before dependent questions when delegation has no supplied branch. Explain single values too. "Horizontal" is not a numeric ratio. Distinguish asset images from final video frames; never copy settings across scopes by assumption.

Do not replace concrete choices with "leave technical matters to the team", "fixed or delegated?", or a recommendation alone before actual delegation. A user's unfamiliarity with models is not delegation and does not justify hiding options. Query current technical capabilities read-only through Creator; no static model catalog in source, invented values or unsupported options. If discovery is blocked, return the technical blocker rather than a generic questionnaire. Consultation-only requests may leave choices open and do not authorize production.

## Continue Within Authority

The actual request establishes target-operation intent without another generation-permission question. Short/series includes necessary asset images and local references after intake/reviews, and always stops before paid video submission. A later manual generate-video request supplies resolved scope and actual conditions for initial_authorization, not generic consent. Config-only, diagnosis-only and preparation-only requests retain their narrower scope.

Image production intent includes same-scope recoverable-failure retries and necessary quality repair, regeneration and fresh independent review, with no default attempt or round limit and no extra retry-authorization question. Requesting one image is not an explicit one-attempt limit. Honor explicit user one-shot/count, scope, checkpoint and financial constraints; paths, diagnosis and retrieval-only requests do not authorize new submissions or replacements.

Diagnose failures and lack of progress; no default limit is not a promise of endless blind attempts. Unsupported parameters, account/quota failures and other nonrecoverable blockers stop affected work. Use alternatives only within fixed configuration and actual delegated authority; otherwise report the blocker. Recover or verify pending/unknown jobs by existing id, never duplicate submissions; polling timeout is not generation failure. Current prompt gates and independent reviews still apply to quality revisions.

Video check/auto only continue registered initial/retry grants and retrieve recorded jobs; they are not new-generation requests. Grants bind `{decision,episode,task_id,shots,constraints}` plus actual optional retry counters. Partial selected-shot groups report task_id, full membership and additional members; never silently expand authorization. Current manifest/record/grant membership must agree before payment. Do not ask retry permission before an otherwise valid initial submission or infer unlimited retries. Ambiguous scope, out-of-scope overwrite, fixed-setting conflicts and protected jobs remain blockers. Generation intent does not delegate parameters. Count generation tasks; human_needed is `{ep,task_id,shots,reason}` with full membership, while monitor scope stays epNN/all.

Once authorized, continue without reasking settled choices, models, limits or retry scope at each stage. Valid ongoing grants cover repeated permitted actions within their actual conditions; an explicitly user-limited one-shot grant does not become ongoing. A request that already authorizes starting needs no final "start?" question. Progress reports are statements, not requests for confirmation.

Independent reviews are automatic internal quality gates, not user approval stages. Director coordinates fixes and fresh independent reviews within the original authority without generic approval after each review or fix. User checkpoints and independent review cannot substitute for each other. The original user-confirmed episode target's +/-10% is an active creative budget, not just tolerance: owners may reallocate scenes/shots for evidence, listening and reactions without per-adjustment permission. Director coordinates canonical script/storyboard and affected references/manifest updates before reuse. Preserve the original baseline in config, never ratchet it from revised or previous episode totals; exact targets, explicit ranges and tighter limits override. See [duration ownership](../../director-orchestrate/SKILL.md#集总时长责任).

For a new blocker, first consult current config, materials and actual grants, then use Director/specialist judgment within authority. Ask the user only at a specified checkpoint or for a consequential conflict, missing authority or unavoidable choice that cannot be resolved that way. Do not escalate speculative questions or undeveloped artistic detail. Pause only affected work; independent authorized work and recorded-job retrieval continue. Initial user duration, fixed models, real scope/overwrite/submission/retry authorization, protected inflight and the separate video entry boundary remain binding.

## Models And User Limits

Setup and all later role creation use the selected models and parameters. Do not require a budget, cost estimate, credit/balance preflight, affordability confirmation or cheapest-option comparison, and do not downgrade to save money. Explicit user-supplied financial limits remain binding; report real account/provider failures without imposing a balance check on every task. Scope, overwrite, initial/retry records, inflight protection and the separate manual video request remain required, not extra generation permission questions. Grant constraints need not contain a financial limit.

Once the user selects a model, assume access for workflow use. Do not check entitlement, membership/VIP, credentials, account state or credits, demand proof, or require acknowledgment of an access-uncertainty disclaimer before using it. This is not a claim of verified access or successful generation. Still validate the installed CLI/API's technical operation/model/ratio/resolution combinations and workflow integration. Only an actual account/provider error in authorized execution triggers reporting and, if necessary, a user decision within existing authority; do not switch a fixed model. Technical discovery must not become an account-access preflight.

## Prepare The Packet

Prepare a decision packet only for a real user decision under the rules above. A status update, internal review result or authorized owner choice does not require a packet or user approval.

The author supplies ALL foreseeable related decision questions together as a complete plan/table, with explicit question boundaries and dependencies. Each question includes exact wording, every option's full explanation and stable short label, context, reasons, risks, uncertainty and a recommendation where useful. Director authors its own creative plans; main preserves expert-authored questions/options without inventing replacements. Labels map one-to-one to full options and remain stable through display, widget and reply. Include financial cost only when user-supplied or relevant to an actual limit/failure or requested comparison, never as an automatic field or question.

A plot-choice question contains all three developed candidates (or the explicit requested count) and a scoped "Director decides" option, not three separate decisions. Main retains the full plan internally and splits presentation only along authored question boundaries, without lossy rewriting or dumping all questions upfront. No new schema is required.

Return the full packet, or an explicit file path and exact section boundaries containing the complete packet. A file reference is transport, not permission to substitute a summary. The originating role remains responsible for making that section complete and unambiguous.

## Present Before Asking

The main AI must read the full plan, including referenced files/sections, then display the complete CURRENT question and all its applicable options, explanations, shared context and qualifications before asking. Other questions remain internal until their turn. A link, path, status summary, or option names alone is insufficient. Preserve authored content intact; formatting and question-boundary splitting only, with no lossy rewriting, merging or selection of preferred excerpts. Filter branches only by the author's explicit conditions, never to hide choices or shorten explanations.

For a long current question, display its full text in ordered parts before the widget; never trim explanations to fit button limits. Label any additional main-AI explanation separately. Then use the available host-native keyboard selector, with exactly ONE item in `questions` and single choice, not Markdown-only asking when a fitting native tool is available. Wait for the answer before presenting the next applicable authored question. Do not issue parallel questions. Collect replies for the related questions and return them together to the original role/context; no per-question owner roundtrip is required.

Return early to the originating role only for missing/unreadable/truncated content or unclear question/answer/branch mappings, incompatible answers, or a new decision outside the supplied plan. Include replies already collected and their conditions; do not reask settled questions. This includes unresolved expert delegation needed for a dependent branch. Do not reconstruct missing content or compatibility from summaries or assumptions, and do not seek a decision on an incomplete question.

## Native Host Mapping

- OpenCode: use `question({questions:[{header,question,options:[{label,description}],multiple:false}]})`. One question only; include all current choices, including delegation. Short descriptions accompany, not replace, the full text. Follow the exposed schema.
- Claude Code: use `AskUserQuestion` when exposed, with exactly one `questions` item, `header`, `question`, `options` of `label`/`description`, and `multiSelect:false`. Respect its current limits. Three plots plus delegation fit a four-option widget.
- Codex: use `request_user_input` only when exposed and legal in the current mode. One `questions` item uses a stable `id`, short `header`, `question`, and `options` of `label`/`description`; respect the exposed limits (commonly 2-3 options and a 12-character header). Do not change mode to enable it. For three plots, show all three in the widget and explicitly explain that "Director decides" is available through its free-text/Other response, if supported. Never hide a candidate to fit delegation. If all choices cannot be represented, disclose the limitation and use the full current packet with a single text-answer fallback; do not silently truncate or paginate the choice set.

If no native question tool is available, or its current mode/schema cannot represent this decision, explicitly disclose that limit, show all current choices and accept one text reply using the same labels. This fallback is not permission to replace an available fitting selector with Markdown. No permission, framework or mode changes to manufacture tool availability.

## Return The Actual Reply

For expert-authored plans, faithfully return the complete batch of original replies, mapped to questions and including every condition, limit, correction, refusal and uncertainty, to the author's original task after related questions (or an early-return blocker). Do not reduce replies to button labels, approval booleans or selections. Main is production Director: preserve expert plans/replies intact without replacing the original specialist, review coordinator or checker context. If that context cannot be resumed, report the blockage rather than inventing continuity. For Director-authored plans, retain and apply the same complete replies locally, without a self-relay.

In unattended monitoring, report that a decision is needed using the existing human_needed/status contract; retain the complete plan separately from compact status output for later interactive handling. Do not initiate unauthorized questions, choose automatically, infer new grants, or expand scope. Interactive handling presents each current question in full before asking, not the entire plan upfront.
